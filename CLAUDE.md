## What this is

Topic Prompt UI is a JavaFX desktop client for sending prompts to OpenAI, GCP (Gemini), and Claude APIs, organizing the resulting Q&A into topics, and rendering answers (grammar/openai/claude/GCP variants) side by side. Built as a Java Platform Module System (JPMS) application with Guice for dependency injection.

## Commands

- Run from IDE: run the `topicpromptui.TopicPromptUiMain` class (module `TopicPromptUi.main`), or use the `TopicPromptUiMain local run` run config.
- Compile tests: `./gradlew compileTestJava`
- Run all tests (unit + integration): `./gradlew test`
- Run unit tests only (skip `*IT.java`): `./gradlew -PskipIntegrationTests test`
- Run integration tests only (`*IT.java`): `./gradlew -PskipUnitTests test`
- Run a single test class: `./gradlew test --tests "topicpromptui.ui.question.SendFactUiTest"`
- Build native image via jlink: `./gradlew -x test clean jlink`
- Full local install (builds, tests, deploys to `~/installed/TopicPromptUI`): `./gradlew installLocally` (or `./gradlew -x test installLocally` to skip tests)
- Redeploy the locally installed app safely: `./deploy-local.sh` — stops any running `~/installed/TopicPromptUI` instance (graceful `SIGTERM`, matched via `pkill -f "installed/TopicPromptUI/bin"`, polls up to 10s for exit) before running `./gradlew -x test installLocally`, since the `installLocally` Gradle task deletes the old `~/installed/TopicPromptUI` directory and copies in the new jlink image but never stops a running process first — a bare `installLocally` while the app is running deletes its jars/launcher out from under it. Prefer this script over calling `./gradlew installLocally` directly when redeploying locally. **It also deliberately deletes `~/.topic-prompt-ui/templates/*.ftl` after installing** — `PromptFactoryImpl` copies each prompt template out of the classpath into `<appData>/templates` only if it isn't already there and then always renders the on-disk copy, so without this the previously materialized copies would shadow every template edit in the new build (the same staleness that `ProjectTemplatesConfigurationModule` works around for the `*ApiIT`s; see "Testing conventions"). The app re-copies the fresh versions on the next request, so a redeploy is all it takes to pick up changes to `src/main/resources/topicpromptui/core/prompt/*.ftl` — but note this discards any hand-edits the user made to the installed templates, which `PromptFactory` otherwise honors as a feature (`PromptFactoryTest.userModifiesTemplate`).
- Cut a release: `./release.sh` — must be run locally (not in CI) with real API credentials in `~/.topic-prompt-ui/config.properties`, since it runs the full `./gradlew test` including integration tests. Requires a clean working tree on `main` with `version.txt` currently holding a `N-SNAPSHOT` version; it then runs tests, commits the release version (`N-SNAPSHOT` → `N`), creates a lightweight tag `vN`, commits the next snapshot (`N` → `N+1-SNAPSHOT`), and prints the `git push`/`git push origin vN` commands to run manually — it never pushes itself.

UI tests use TestFX (`ApplicationTest`) and need a display. The Gradle `test` task starts (and tears down) its own throwaway Xvfb + openbox virtual display by default — no windows open on the desktop, locally or in CI (CI just installs the `xvfb`/`openbox` packages; see `.github/workflows/gradle.yml`). Pass `-PonRealDisplay` to watch the tests on the current `DISPLAY` instead.

Integration tests (`*IT.java`, e.g. `OpenAiApiIT`, `ClaudeApiIT`, `GcpApiIT`, `SoundServiceIT`) hit real external services/APIs and require credentials in `~/.topic-prompt-ui/config.properties` (`openai.token`, `claude.api.key`, `gcp.api.key`); they are excluded by `-PskipIntegrationTests` and are not run in CI. If `~/.topic-prompt-ui/config.properties` on the local machine already has all three credentials populated, these tests are directly runnable via `./gradlew test` — don't assume they're unrunnable and skip straight to `-PskipIntegrationTests`; try running the relevant `*ApiIT` class first.

## Git workflow

**Always commit to the current branch — never create a new branch first, even when on `main`.** This is a single-contributor repo whose release/deploy tooling (`release.sh`, `deploy-local.sh`) operates directly on `main`, so the default "branch before committing on the default branch" behavior only adds unwanted merge friction here. When the user says "commit", commit in place on whatever branch is checked out.

## Code quality

SonarCloud project: https://sonarcloud.io/project/overview?id=Aleks-Ya_topic-prompt-ui — check here for code quality/coverage metrics and issues.

**Only write comments that carry information the code cannot.** Explain *why* — a non-obvious constraint, a gotcha, a rejected alternative, an external quirk — never *what* the next line already says. No comments that restate a method name, narrate obvious steps, label sections of a method, or announce that code was added/changed. Javadoc follows the same bar: write it when a type/method has a contract or a subtlety worth stating, skip it when it would only echo the signature. This applies to test code too. Prefer a clearer name or a smaller method over a comment that compensates for an unclear one.

**Adding a new dependency is fine when a well-established library meaningfully simplifies the code** — the user prefers a small extra dependency over a hand-rolled implementation of something a library already does well. Remember that a new library needs the `implementation` entry in `build.gradle`, a `requires` in `module-info.java`, possibly an `extraJavaModuleInfo` entry (only if the jar declares no `Automatic-Module-Name` of its own), and a `./gradlew -x test clean jlink` run to prove it links into the native image.

## Claude Code hooks

`.claude/settings.json` logs hook payloads to `build/PostToolUse-log.json` / `build/FileChanged-log.json` and auto-renders edited PlantUML diagrams.

**`FileChanged` hook matcher semantics are unusual** (verified against Claude Code 2.1.202 internals): the `matcher` string does double duty. It is split on `|` and each piece is used as a **literal filesystem path to watch** (absolute, or relative to the project root; no glob support — the bundled chokidar v4 treats `*` as a literal filename), and the whole string is *also* re-used as a regex filter against the changed file's **basename** at dispatch time. Hence the matcher `"src|docs|.*"`: `src` and `docs` are the watched directories (recursive), and the `.*` alternative makes the dispatch regex match every changed file (it contributes a harmless nonexistent watch path). A bare `"*"` matcher never fires — it watches a literal file named `*`. Two more gotchas: the watch list is built **once at session startup**, so matcher changes need a session restart (unlike other hooks, which hot-reload); and never watch `build/` or the project root, or the hook's own log write would re-trigger it in a loop.

## Architecture

Strict layered MVVM, one-way dependency flow: **view → viewmodel → mediator → model → core**. Each layer only talks to the layer directly below/adjacent to it.

- `topicpromptui.core.ai` — `AiApi` interface with three provider implementations (`openai`, `claude`, `gcp`), each with its own Guice module, request/response DTOs, and Freemarker-based prompt building. Model names are hardcoded per binding inside each `*Module` (`OpenAiModule`, `ClaudeModule`, `GcpModule`) via manual `new XApiImpl(model)` + `toInstance(...)` (not compiled into the impl classes) — this lets `OpenAiModule` bind two `AiApi` instances (`AiModule.OPEN_AI` and `AiModule.OPEN_AI_GRAMMAR`) with different models, so `AnswerType.GRAMMAR` can use a cheaper/faster model than `AnswerType.OPEN_AI`.
- **Reasoning effort** is likewise hardcoded per binding: each `*ApiImpl` constructor takes an extra effort/thinking-level enum parameter (OpenAI: `ReasoningEffort` in `openai/RequestBody.java`; Claude: `Effort` nested under `output_config` in `claude/RequestBody.java`; GCP: `ThinkingLevel` nested under `generationConfig.thinkingConfig` in `gcp/RequestBody.java`), set as a `private static final` constant in the corresponding `*Module`. Passing `null` omits the field from the JSON request body entirely (Gson's default `new Gson()` skips null fields, no `serializeNulls()` configured) so the provider falls back to its own default effort/thinking level instead of an explicit value.
- **Model metadata and token usage are persisted for troubleshooting.** `AiApi.send(...)` returns `AiResponse(text, responseId, modelId, effortLevel, inputTokens, outputTokens, totalTokens)` — `modelId`/`effortLevel` come from each `*ApiImpl`'s own `model`/`effort` constructor fields (not echoed-back response data, since GCP's response never repeats the model), and the token counts are parsed from each provider's real usage JSON (`openai/ResponseBody.Usage` — `input_tokens`/`output_tokens`/`total_tokens`; `claude/ResponseBody.Usage` — `input_tokens`/`output_tokens`, with `totalTokens` computed as their sum since Claude's API doesn't return one; `gcp/ResponseBody.UsageMetadata` — `promptTokenCount`/`candidatesTokenCount`/`totalTokenCount`, where `totalTokenCount` can exceed `prompt+candidates` because Gemini's thinking models fold internal "thoughts" tokens into the total without breaking them out separately). `QuestionModelImpl` copies all 5 fields onto the stored `Answer` via `Answer.withModelInfo(...)` alongside the existing `withResponseId(...)` call, in both `requestAnswer` and `requestFollowUpAnswer`.
- `topicpromptui.core.domain` — the app's shared domain vocabulary: the pure records/enums `Interaction`, `Answer`, `Topic`, `InteractionId`, `TopicId`, `InteractionType`, `AnswerType`, `AnswerState`. Its only outgoing dependency is on the leaf `core.util` package (`LogUtils.shorten`, used in `Interaction`/`Answer`), so every layer above can import it without creating a cycle. These types were previously in `core.storagefilesystem`; they were extracted here because they're imported across `ui.model`/`ui.viewmodel`/`ui.view` and naming their home after one persistence mechanism was misleading. Note `core.ai` deliberately does **not** depend on `core.domain` — it keeps its own DTOs (`AiResponse`, `ConversationTurn`/`Speaker`), and `QuestionModel` is the bridge that maps domain ↔ AI DTOs. JPMS: `module-info` `exports topicpromptui.core.domain` and `opens ... to com.google.gson` (Gson reflects over the records for `Interaction`/`Topic` JSON); no Guice `opens` since nothing here is Guice-injected.
- `topicpromptui.core.storagefilesystem` — `StorageFilesystem`: JSON-on-disk persistence (via Gson) for `Interaction`s and `Topic`s, under `<appData>/storage`. Depends downward on `core.domain` for those types; the package-private Gson adapters `InteractionIdSerDe`/`TopicIdSerDe` (keyed off `InteractionId`/`TopicId`, registered in `StorageFilesystemImpl`) live here as a persistence detail.
- `topicpromptui.core.config` — `ConfigModel`/`ConfigModelImpl`/`ConfigurationModule`: reads `~/.topic-prompt-ui/config.properties` (API keys) and resolves the app data path (`~/.topic-prompt-ui`). Lives under `core` (not `ui.model`, despite the `*Model`-style naming) because it's consumed by `core.ai`'s three provider impls and by `core.storagefilesystem.StorageFilesystemImpl` — putting it in `ui.model` would make those `core` packages depend back up on `ui`, breaking the one-way layering below. `core.prompt.PromptFactoryImpl` also uses it (both are `core` packages).
- `topicpromptui.core.prompt` — `PromptFactory`/`PromptFactoryImpl`/`PromptModule`: builds the actual prompt/system-prompt text from the Freemarker templates in `src/main/resources/topicpromptui/core/prompt/`, keyed off the `(InteractionType × AnswerType)` matrix (see "AnswerType / prompt templates"). Lives under `core` (moved here from `ui.model.question.prompt`) rather than in the model layer because prompt-building is a core concern consumed by `ui.model.question.QuestionModelImpl`, a legitimate downward `model → core` dependency. Depends on `core.config` (app-data path for template caching), `core.domain` (`InteractionType`/`AnswerType`), and `core.util`. Deliberately **not** placed under `core.ai`: `core.ai` keeps itself free of any `core.domain` dependency (see the `core.ai` bullet), and `PromptFactory`'s signatures are all `core.domain` vocabulary, so folding it into `core.ai` would break that separation — hence a sibling `core.prompt` package instead. JPMS: `exports`/`opens ... to com.google.guice` in `module-info`.
- `topicpromptui.core.sound` — `SoundService`/`SoundServiceImpl`/`SoundModule`: plays a short synthesized completion beep (`javax.sound.sampled`, tone generated in memory — no audio resource files) when an answer finishes, keyed by `AnswerType`. Consumed by `ui.model.question.QuestionModelImpl` (a `model → core` dependency). Lives under `core` (moved here from `ui.model.question.sound`) rather than in the model layer because it has no UI/JavaFX dependency — only `core.domain.AnswerType` plus JDK audio — so it's a side-effecting service peer to `core.ai`/`core.storagefilesystem`, and the old `question.` nesting was incidental. Tests: `SoundServiceTest`, `SoundServiceIT` (plays real audio), and `SoundServiceMock` (swapped in by `TestRootModule`), all under `test/.../core/sound/`. JPMS: `exports`/`opens ... to com.google.guice` in `module-info`.
- `topicpromptui.ui.model` — business/domain layer: `StateModel` (current interaction/topic selection state), `StorageModel` (wraps `StorageFilesystem`), `QuestionModel` (orchestrates sending questions to `AiApi` per `AnswerType`), `FileModel`, `ClipboardModel`. Each has its own subpackage with an interface, an `*Impl`, and a Guice `*Module`.
- `topicpromptui.ui.viewmodel.mediator` — the hub. `MediatorImpl` implements six narrow mediator interfaces (`HistoryMediator`, `QuestionMediator`, `TopicMediator`, `AnswerMediator`, `TopicPromptUiMediator`, `TopicPromptUiApplicationMediator`), one per viewmodel area. Viewmodels never touch models directly; they call through their specific mediator interface. This is the layer to touch when a user action needs to fan out across multiple viewmodels (e.g. `displayCurrentInteraction()` refreshes history, question, topic, and all four answer panes).
- `topicpromptui.ui.viewmodel.{answer,history,question,topic,ui,uiapp}` — one subpackage per UI area, each following the same triad: `*VmController` (what the view calls), `*VmMediator` (what the mediator calls back into), `*VmImpl` (implements both), `*Properties` (JavaFX observable properties bound by FXML), `*Module` (Guice bindings). There are 4 parallel `AnswerVm` instances (`AnswerVmModule.GRAMMAR/OPEN_AI/CLAUDE/GCP`), all bound via `@Named` qualifiers to the same interfaces.
- `topicpromptui.ui.view` — FXML controllers (`TopicPromptUiController`, `HistoryController`, `QuestionController`, `TopicController`, `AnswerController`) plus `TopicPromptUiApplication`, the JavaFX `Application` entrypoint that boots the Guice context (`RootModule`) and loads `TopicPromptUi.fxml`.
- `topicpromptui.RootModule` — top-level Guice module, installs `ModelModule`, `ViewModelModule`, `ViewModule` in that order. `binder().requireExplicitBindings()` is set, so every injected type must be explicitly bound in some module.
- `docs/*.puml` — PlantUML diagrams documenting this layering; consult these before making cross-layer changes. Class diagrams: `mvvm-answertype-fanout.puml` (4 parallel `AnswerVM`/`AnswerController` per `AnswerType`), `mvvm-mediator-overview.puml` (mid-level view with generic `AnswerVM` and model-layer internal deps), `mvvm-interfaces-detailed.puml` (most detailed, matches current code: `*VmController`/`*VmMediator` interfaces per area, `ViewModelMediatorImpl` implementing the six mediator interfaces), `question-model-collaborators.puml` (`QuestionModel`'s dependencies). Package-level: `package-layer-dependencies.puml`. Sequence: `thread-model-sequence.puml` (thread hops during `requestAnswer()`).

### AnswerType / prompt templates

`AnswerType` (`GRAMMAR`, `OPEN_AI`, `CLAUDE`, `GCP`) drives parallel behavior throughout the stack: 4 `AnswerVm` bindings, 4 answer panes in the FXML, and Freemarker prompt templates in `src/main/resources/topicpromptui/core/prompt/` — one **user-message** template per interaction type (`question.ftl`, `definition.ftl`, `fact.ftl`, `grammar.ftl`) plus the parallel `*-system.ftl` system templates. `PromptFactory` builds the actual prompt text sent to `AiApi` from these templates.

**System-prompt split.** Prompts are split into a **system prompt** (stable behavioral instructions — "Format into Markdown", "Do not repeat the question", the grammar rules, etc. — **plus the topic**) and a **user message** (just the question). The user templates are slimmed to question-only, and — because the split left them with no provider- or type-specific instructions — they are **one per interaction type and provider-independent** (`question.ftl`, `definition.ftl`, `fact.ftl`, plus `grammar.ftl` shared by every interaction type's `GRAMMAR` answer). The instructions live in parallel per-*interaction-type* system templates (`question-system.ftl`, `definition-system.ftl`, `fact-system.ftl`, `grammar-system.ftl`, shared across providers since the content is identical per type; `grammar-system.ftl` is likewise shared across all interaction types' grammar checks). **The topic lives in the system prompt, not the user message** (`question-system.ftl`/`definition-system.ftl`/`fact-system.ftl`/`grammar-system.ftl` all interpolate `` `${topic}` ``; the `grammar.ftl` user template carries only the question): because the system prompt is reasserted on every turn, the topic stays anchored throughout a follow-up chain instead of only appearing in turn 1's replayed user message — and the Topic combobox is locked while Follow-up is checked (see "Follow-up requests"), so a chain's topic is constant and safe to restate each turn. The grammar templates moved the topic to their system template too even though grammar checks are single-shot and never a follow-up, purely for consistency across the whole `(InteractionType × AnswerType)` matrix. `PromptFactory` exposes both `getPrompt(interactionType, question, answerType)` (user message) and `getSystemPrompt(interactionType, topic, answerType)` (system prompt); both mirror the same `(InteractionType × AnswerType)` matrix and return `Optional.empty()` for the interaction-`GRAMMAR` × non-grammar skip case. `getPrompt` deliberately takes **no** `topic` — the topic lives only in the system prompt now, and none of the user-message templates interpolate `${topic}`, so it was dropped as a dead parameter (the asymmetry with `getSystemPrompt`, which still needs `topic`, is intentional). `QuestionModelImpl` passes `storage.getTopic(interaction.topicId()).title()` to `getSystemPrompt` on **both** the initial (`requestAnswer`) and follow-up (`requestFollowUpAnswer`) paths. The system prompt is threaded to each provider's native field via `AiApi.send(String systemPrompt, List<ConversationTurn>, Consumer<String>)` — Claude top-level `system`, OpenAI Responses `instructions`, GCP `systemInstruction` (a `Content` with `role=null`); a `null` systemPrompt omits the field (Gson skips nulls) so the provider uses its default. It is applied on **both** the initial and follow-up paths, so the instructions are reasserted every turn instead of decaying with distance from turn 1. **Test gotcha**: the mock APIs (`BaseMockApi`) now match request types against the combined `systemPrompt + "\n" + lastUserMessage` (the distinguishing phrases moved from the user template into the system prompt), and `getSystemPromptHistory()` records what was sent; `AssertJ`'s `Optional.contains(x)` is value-*equality*, so `PromptFactoryTest` unwraps with `orElseThrow()` before substring-`contains`.

### Topic combobox suggestion ordering

The Topic combobox is a ControlsFX `SearchableComboBox`. While the user types in its popup search field, suggestions are ordered shortest-title-first (exact match "AWS" above "AWS EC2"); with an empty search text the items' own MRU order is untouched. ControlsFX's `SearchableComboBoxSkin` only filters (fresh `FilteredList` per keystroke, source order preserved) and its members are private in a non-exported package (`impl.org.controlsfx.skin` is a qualified export), so `topicpromptui.ui.view.SearchableComboBoxShortestFirst` hooks the skin's child nodes by their stable ids — the internal `ComboBox` `#filtered` and search `TextField` `#search` — via `lookup()` once the skin attaches, and re-wraps the filtered list in a `SortedList` (stable, so equal lengths keep MRU order). It fail-softs (warn + stock behavior) if the ids vanish; re-verify on ControlsFX upgrades (`SearchTopicShortestFirstUiTest` is the tripwire). **Gotcha that cost a debugging session**: the items hook must be an `InvalidationListener`, not a `ChangeListener` — the skin replaces one `FilteredList` with another whose content is often `equals()` (element-wise `AbstractList.equals`), and JavaFX suppresses `ChangeListener` notifications for equal old/new values, so a change listener silently never fires.

### History filter text field

`#historyFilterTextField` (in `History.fxml`, right of the History combo) live-filters the History dropdown by case-insensitive substring match on `Interaction.question()` only (not topic title / type prefix); blank text = no filtering. The filter state lives in `StateModelImpl.historyFilterText` and is applied inside `getFilteredHistory()`, ANDed with the topic filter checkbox — so everything downstream of `getFilteredHistory()` (delete-neighbor picking, `chooseFirstInteractionAsCurrent`, the `(filtered/full)` label) respects it for free. Wiring: `HistoryVmImpl` listens on `HistoryVmProperties.historyFilterTfText` per keystroke (TextField has no per-keystroke `onAction`) with the guarded-write pattern, then refreshes only the History area — deliberately no mediator fanout, because **typing never changes the current interaction**: if the current interaction is filtered out, the answer panes keep showing it and only the combo selection is cleared (a membership check in `HistoryComboBoxFacade.selectCurrentInteraction()` — JavaFX `ComboBox` would otherwise happily select a value absent from `items`); clearing/relaxing the filter re-selects it automatically. `Ctrl-F` focuses the field and selects its text (so typing replaces the old filter); like `Ctrl-1..4` it is wired twice — scene accelerator in `MediatorImpl.addShortcuts` **and** `AnswerController.onWebViewKeyPressed` — because a focused WebView consumes key events before accelerators fire. Tests: `FilterHistoryByQuestionTextUiTest`, `FilterHistoryByQuestionAndTopicUiTest`, `HistoryFilterTextUiTest`, the `Ctrl-F` tests in `HotKeysUiTest`; `WindowAssertion.modelCurrentInteraction(...)` exists because the model-current interaction and the combo selection legitimately diverge while the filter hides the current one.

### Grammar checking

The user is not a native English speaker, so the app always grammar-checks their questions. The app never auto-corrects the question before sending it — the original text is what's sent to the AI models; the corrected version is only ever displayed in the `Grammar` answer panel for reference, and the user can choose to manually re-send the corrected version as a new question if they want.

There are 4 question-submission buttons in the UI: **Question**, **Definition**, **Fact**, **Grammar**. `Grammar` sends only a grammar-check request. `Question`, `Definition`, and `Fact` each send two things: a grammar-check request, and the question request (original text, unmodified) fanned out to all 3 AI models (OpenAI, Claude, GCP). A separate **Resend** button repeats the last request, for recovering from failures.

**The changed words are bolded in code, not by the LLM.** `grammar-system.ftl` asks only for the corrected sentence (or the exact `Correct` sentinel) and says nothing about formatting; `GrammarDiffMarker` (package-private in `ui.model.question`, self-bound in `QuestionModule` next to `FormatConverter`) then word-diffs the answer against `interaction.question()` and wraps the changed words in `**`. This replaced four prompt guidelines that the model kept getting wrong (bolding whole clauses, bolding unchanged words, missing changed ones) — a string diff is deterministic, a prompt rule is not. Details worth knowing:
- Uses `io.github.java-diff-utils:java-diff-utils` (`DiffUtils.diff` over `\S+` tokens): INSERT/CHANGE deltas bold the added or substituted words; a DELETE delta bolds the words on either side of the gap, since nothing of a removed word survives to bold (this reproduces the old prompt's removal rule: `I **discussed the** problem with the team.`). Adjacent bolded words merge into one span, but never across a newline — a Markdown bold span can't straddle a line break. The jar declares its own `Automatic-Module-Name` (`io.github.javadiffutils`), so `module-info` just `requires` it and it must **not** be listed in `extraJavaModuleInfo` — re-declaring the name fails `ExtraJavaModuleInfoTransform`.
- `markChanges` **strips any `**` the model emitted anyway** before diffing, because `PromptFactoryImpl` renders the on-disk template copy: an installed app keeps serving the old bolding prompt until `~/.topic-prompt-ui/templates/*.ftl` is deleted (which `./deploy-local.sh` does).
- The diff needs the whole answer, so the streaming preview (`ProgressThrottler`) stays raw and the marks appear when the answer completes. Mechanically this is a `UnaryOperator<String> postProcessMd` argument to `QuestionModelImpl.sendAsync`, applied on the SUCCESS path only (identity for every non-GRAMMAR answer and for follow-ups). It diffs `interaction.question()`, **not** `answer.prompt()`, which holds the `<sentence-or-phrase>`-wrapped template output.
- Test fallout to expect when touching this: every UI test whose mock grammar response is unrelated to the typed question now gets it fully bolded. `TestingData.I*.GRAMMAR_ANSWER` (= the question itself, i.e. "no mistakes found") plus `EXP_GRAMMAR_ANSWER_BODY` exist for exactly that; `SendGrammarUiTest` deliberately mocks a real correction and asserts the `<strong>` end to end, and `GrammarDiffMarkerTest` covers the diff rules directly.

### Expanded answer pane

Each answer pane has a ⛶ toggle button (`#expandButton` in `Answer.fxml`) that expands it to fill the whole window; Esc collapses it (when nothing is expanded, Esc keeps its focus-question behavior — conditional dispatch in `MediatorImpl.escapePressed`). `Ctrl-1..4` also toggles expansion per pane, with the same digit→pane mapping as the `Alt-1..4` copy shortcuts (`AnswerVmImpl.hotkeyDigitMap`). The Ctrl-digit hotkey is wired twice on purpose: as scene accelerators in `MediatorImpl.addShortcuts`, **and** in `AnswerController.onWebViewKeyPressed` (→ `AnswerVmController.ctrlDigitHotkeyPressed`), because a focused `WebView` consumes key events before scene accelerators see them (the same reason `Ctrl-Alt-Up/Down` live in that filter); the filter consumes the event, so the accelerator never double-fires. The state is a single nullable `ObjectProperty<AnswerType> expandedAnswerType` in `TopicPromptUiVmProperties` (`ui.viewmodel.ui` area, owned by `TopicPromptUiVmImpl` which implements both `TopicPromptUiVmController` and the added `TopicPromptUiVmMediator`) — one property instead of 4 booleans makes "at most one pane expanded" structural. All Node manipulation lives in `TopicPromptUiController.onExpandedAnswerChanged`: a generic loop over `rootVBox` children toggles `managed`/`visible`, and the expanded pane's `maxHeight`/`VBox.vgrow` are saved and restored (this is what lifts the grammar pane's `70`/`SOMETIMES` cap while it's expanded). Two gotchas: (1) never touch `visible` on the `Separator` children — they are invisible spacers (`visible="false"` in `TopicPromptUi.fxml`) and must stay invisible after restore; unmanaging them is enough to reclaim their space; (2) in `TopicPromptUi.fxml` the include roots' node ids are **not** always the `fx:include fx:id` — History/Question set their own root `fx:id`s (`historyHBox`/`questionHBox`) which win over the include's, so `ExpandAnswerUiTest` locates the non-answer panes by walking up from a known child to the direct child of `rootVBox` instead of by id. Hidden panes keep streaming/updating fine (bindings and `WebView.loadContent` work on invisible nodes), so no guards were needed.

### Follow-up requests

`Interaction` has a nullable `parentInteractionId` field (links a follow-up to the interaction it continues) and `Answer` has a nullable `responseId` field (each provider's response id — OpenAI `resp_...`, Claude `msg_...`, GCP `responseId`, all confirmed live). The thread model is a chain of separate linked `Interaction`s (one per turn, `parentInteractionId` pointing at the previous turn), not a multi-turn container inside a single `Interaction` — this keeps the 1-file-per-interaction storage layout and the 4-parallel-`AnswerVm` architecture unchanged.

**UI trigger**: a "Follow-up" `CheckBox` (`fx:id="followUpCheckBox"` in `Question.fxml`, `QuestionVmProperties.followUpCheckBoxSelected`) sits next to the Resend button, mirroring the existing `filterHistoryCheckBox`/`bindBidirectional` pattern in `Topic.fxml`. When checked, clicking **Question**/**Definition**/**Fact** creates a new `Interaction` whose `parentInteractionId` is whatever's currently displayed/selected (`mediator.getCurrentInteractionId()`) instead of `null` — `QuestionVmImpl.createNewInteractionAndRequestAnswers` computes this and passes it through `StateModel`/`QuestionMediator.createInteraction(InteractionType, InteractionId parentInteractionId)`. **Grammar** is unaffected (grammar-checking is never a follow-up).

**Topic combobox is locked while Follow-up is checked** — a follow-up inherits its parent's topic (`createInteraction` uses the current topic, which equals the displayed parent's), so the combobox is disabled to prevent diverging from it (this is what lets the topic ride in the reasserted-every-turn system prompt; see "AnswerType / prompt templates"). Wiring is cross-area through the mediator, matching the `toggleFollowUp` pattern: the existing `followUpCheckBoxSelected` listener in `QuestionVmImpl` calls `QuestionMediator.setTopicComboBoxDisabled(boolean)` → `MediatorImpl` → `TopicVmMediator.setTopicComboBoxDisable(boolean)` → `TopicVmProperties.topicComboBoxDisable`, bound to `topicComboBox.disableProperty()` in `TopicController`. Driving it off that one listener covers every toggle path (mouse click, `Alt-U`, and `displayCurrentInteraction()` syncing the checkbox to the displayed interaction), so viewing an existing follow-up also disables the combo. Test: `DisableTopicComboBoxForFollowUpUiTest`.

Key design point: **Resend and each answer pane's ⟳ regenerate button needed zero code changes.** They already funnel through the single `QuestionModel.requestAnswer(interactionId, answerType, callback)` regardless of which interaction is targeted; `requestAnswer` itself now checks `interaction.parentInteractionId() != null && answerType != GRAMMAR` at the top and internally delegates to `requestFollowUpAnswer` when true. The follow-up/non-follow-up distinction is a pure data concern (what's stored on the `Interaction`), not something the mediator/viewmodel/view layers need to know about.

`requestFollowUpAnswer` deliberately skips `PromptFactory`/FreeMarker templating of the *user message* and sends `interaction.question()` verbatim as the new turn's text — re-wrapping the follow-up text in the same template would be redundant. Only the very first message of a conversation (sent through plain `requestAnswer`) has a templated user message; every subsequent follow-up turn is raw user text. **But the behavioral instructions and the topic ride in the system prompt, not the user message** (see "AnswerType / prompt templates"), so `requestFollowUpAnswer` still calls `promptFactory.getSystemPrompt(interaction.type(), storage.getTopic(interaction.topicId()).title(), answerType)` and passes it to `send(systemPrompt, turns, ...)` — the follow-up interaction's own `type()` and `topicId()` pick the system prompt, and it is reasserted on every follow-up turn.

Follow-up interactions are marked in the History combo box with a `↳ ` prefix (`InteractionItem.toString()`, `topicpromptui.ui.viewmodel`) so users can tell them apart from independent interactions.

**Hotkey (`Alt-U`) is a Scene accelerator, not an FXML mnemonic** — deliberately, because `CheckBox` mnemonics are broken in this JavaFX version: the Scene's automatic underscore-mnemonic system dispatches a plain `ActionEvent` to the target rather than calling the control's `fire()`, and `CheckBox`'s "toggle `selected`" logic lives specifically inside its overridden `fire()`, so mnemonic activation silently does nothing (confirmed empirically — reproduced with multiple different mnemonic letters, ruling out a text-parsing quirk specific to "U" or the hyphen in "Follow-up"). `Button` mnemonics work fine because `onAction` *is* the whole behavior, so a raw `ActionEvent` is sufficient. The fix: `followUpCheckBox` keeps `mnemonicParsing="false"`, and `MediatorImpl.addShortcuts` registers `Alt-U` as a `KeyCodeCombination` in `scene.getAccelerators()` (the same mechanism already used there for `Ctrl-Alt-Up/Down`, `Ctrl-Alt-V`, `Esc`, `Ctrl-Enter`), wired to a new `QuestionVmMediator.toggleFollowUp()` that flips `followUpCheckBoxSelected` directly. If a future checkbox/toggle needs a hotkey, follow this same accelerator pattern rather than an FXML mnemonic.

`responseId` is captured purely as informational/debugging metadata, **not** used for conversation continuation. OpenAI's Responses API supports resuming via `previous_response_id`, but OpenAI's server-side response retention is time-limited (~30 days), so relying on it would silently break follow-ups to older interactions. Instead, all three providers reconstruct full conversation history by walking the `parentInteractionId` chain and reusing each ancestor `Answer`'s existing `prompt`/`answerMd`.

The actual sending mechanism is built and tested, at the model/core layer only (`topicpromptui.core.ai`, `topicpromptui.ui.model.question`) — no `topicpromptui.ui.view`/`topicpromptui.ui.viewmodel` changes:
- `AiApi.send(String)` is now a `default` method delegating to `AiApi.send(List<ConversationTurn> turns)` (`ConversationTurn(Speaker, content)`, `Speaker` is `USER`/`MODEL`) — itself now a `default` onto the streaming 2-arg method, which in turn `default`s onto the 3-arg `send(String systemPrompt, List<ConversationTurn>, Consumer<String>)` with `systemPrompt = null` (see "Streaming answers (SSE)" and "AnswerType / prompt templates"). Each provider impl overrides the 3-arg method, maps `Speaker` to its own role vocabulary (OpenAI/Claude: `user`/`assistant`; GCP: `user`/`model`) and always builds the full turn list — OpenAI's `RequestBody.input` is `List<InputItem>` (Responses API accepts an array of `{role, content}` items, not just a plain string), Claude/GCP already had array-shaped request bodies.
- `FollowUpHistoryBuilder` (package-private, in `topicpromptui.ui.model.question`, mirrors the `FormatConverter` self-bind-in-`QuestionModule` pattern) walks the `parentInteractionId` chain via `StorageModel` and reconstructs the turn list for a given `AnswerType`, throwing `IllegalStateException` if an ancestor lacks a `SUCCESS` answer for that type.
- `QuestionModel.requestFollowUpAnswer(InteractionId, AnswerType, Runnable callback)` mirrors `requestAnswer`'s async structure but requires a non-null `parentInteractionId`, builds history via `FollowUpHistoryBuilder`, appends the new prompt as a final `USER` turn, and calls `send(systemPrompt, turns, ...)`. `GRAMMAR` is intentionally unsupported (throws) since grammar-checking isn't a conversation.

Test-only note: any test exercising `QuestionModelImpl` (real or follow-up) must run with a live JavaFX toolkit, since `updateAnswer` calls `Platform.runLater` — extend `ApplicationTest` directly (see `RequestFollowUpAnswerTest`, mirroring `ClipboardModelTest`) rather than plain `BaseTest`, without booting the full `TopicPromptUiApplication`/FXML scene like `BaseTopicPromptUiTest` does. `BaseMockApi` also now exposes `getTurnsSendHistory()` (full `List<ConversationTurn>` per call, not just the last message's text) for asserting multi-turn payloads were built correctly.

### Server-side tools (web search, web fetch, MCP)

All tool use is **provider-hosted** — there is no client-side tool loop, and adding one would be a large change (all three providers model a turn as `role` + plain `String` content: Claude `Message`, OpenAI `InputItem`, GCP `Content`; `ConversationTurn.Speaker` has only `USER`/`MODEL`; and `AiResponse.toolCalls` is already-formatted display text, so the tool id and structured args are gone by the time a response leaves the impl).

Each `*ApiImpl` takes a **`toolsEnabled`** constructor flag (hardcoded per binding in its `*Module`, like `MODEL`/`EFFORT`) gating every server-side tool. It is `false` only for `AiModule.OPEN_AI_GRAMMAR` — a grammar check is single-shot, latency-sensitive, runs on a cheaper model, and never needs a lookup. Context7 additionally requires `context7.api.key`, so a binding with tools on but no key still gets the web tools.

| Provider | Tools sent | Where the tool calls come back |
|---|---|---|
| Claude | `web_search_20260209`, `web_fetch_20260209`, plus `mcp_toolset` for Context7 | `server_tool_use` content blocks (web) / `mcp_tool_use` (Context7), input via `input_json_delta` |
| OpenAI | `web_search`, plus the hosted `mcp` tool for Context7 | `web_search_call` outputs (query/url in `action`) / `mcp_call` outputs |
| GCP | `googleSearch`, `urlContext` | `candidates[].groundingMetadata.webSearchQueries` |

- **Claude's `RequestBody.Tool(type, name, mcp_server_name)`** is one record covering both shapes — Gson's null-skipping makes the unused field disappear. Same trick for **GCP's `Tool(googleSearch, urlContext)`**: Gemini keys built-in tools by *field name* with an empty object as config, so a null field must vanish rather than serialize as `"googleSearch": null`. **OpenAI needed no request DTO change** — `new Tool("web_search", null, null, null, null)` already yields `{"type":"web_search"}`.
- Claude's `_20260209` web tools do dynamic filtering via an internal code-execution pass, so **do not also declare a `code_execution` tool** — a second execution environment confuses the model. They need no beta header on `claude-opus-5`; the `anthropic-beta: mcp-client-2025-11-20` header stays keyed on `mcp_servers != null`.
- **The request `.timeout(...)` was raised from 1 to 3 minutes on all three impls.** It bounds time-to-headers only (bodies are read via `BodyHandlers.ofLines()`), and a grounded Gemini turn runs its search *before* emitting the first SSE byte — 1 minute reproducibly timed out mid-search.
- **Gemini decides for itself whether to ground**, and telling it to search is not enough: asked for something it believes it knows (e.g. the current Node.js version) it answers from memory and returns no `groundingMetadata` at all. Only a question that genuinely needs live data triggers grounding — hence `GcpApiIT.sendWithWebSearch` uses a deliberately time-bound "today's headlines" prompt. Confirmed against the raw API, not inferred.
- **Attaching tools shifts answer verbosity even when nothing is searched**, in opposite directions per provider: on "Give me the name of the Java creator" Claude went from under 500 to 623/634 chars, while Gemini tightened from ~136-173 to ~62 (3/3 each way via curl). The tool definitions sit in the prompt prefix and change the answering posture. Only the `*ApiIT.send()` tests, which pass `systemPrompt = null`, were affected — their length ranges were relaxed with a comment; the `definition*()` tests that send a system prompt were unchanged, as is the app, which always sends one. **Expect this when adding or removing a tool: re-check the no-system-prompt ITs.**
- No `module-info.java` or `build.gradle` change was needed (no new package, no new dependency), and the UI needed none either — the new calls flow through the existing `AiResponse.toolCalls` → `Answer.toolCalls` → "Tools used" `TextArea` path for free.

### Streaming answers (SSE)

All three providers stream **always** — there is no non-streaming code path. `AiApi.send(String systemPrompt, List<ConversationTurn>, Consumer<String> onTextDelta)` is the abstract method; the 1-arg/2-arg/list `send` overloads are `default`s delegating with a no-op consumer and a `null` system prompt, which reproduces the old blocking behavior exactly (the call still blocks on the executor thread and returns the complete `AiResponse`). SSE framing (`event:`/`data:` folding, `[DONE]`/comment skipping) lives in the shared `topicpromptui.core.ai.SseParser`; event *interpretation* stays per-provider in a package-private `assemble(Stream<String>, Consumer<String>)` next to each impl (unit-testable without HTTP — see `ClaudeApiImplTest`):

- **Claude**: `RequestBody.stream=true`; `message_start` → responseId + input tokens, `content_block_delta`/`text_delta` → deltas, `message_delta` → stop_reason + output tokens (`claude/StreamEvent` DTO — the old non-streaming `ResponseBody` was deleted).
- **OpenAI**: `RequestBody.stream=true`; `response.output_text.delta` → deltas; the final `response.completed` event carries the full old `ResponseBody`, so `parseResponse` is reused verbatim; `response.failed`/`response.incomplete` → `AiApiException`.
- **GCP**: endpoint changed to `:streamGenerateContent?alt=sse` (no body change); each `data:` line parses with the existing `ResponseBody`; concatenate **all** `parts[].text` per fragment (don't assume one part); the final fragment carries `finishReason`/`usageMetadata`/`responseId`.

Gotchas encoded in the impls: mid-stream provider errors arrive as SSE events on an HTTP **200** (Claude `error`, OpenAI `response.failed`) and must be mapped to `AiApiException`, or truncated answers would be persisted as SUCCESS; all impls read via `HttpResponse.BodyHandlers.ofLines()`, so the JDK request `.timeout(1min)` now only bounds time-to-headers, not generation length (long generations no longer time out); a mid-stream disconnect surfaces as `UncheckedIOException` from the line stream and is wrapped into `AiApiException`.

**UI path for partial answers** (respects the layering — models still only receive plain callbacks): `QuestionModel.requestAnswer/requestFollowUpAnswer` gained 4-arg overloads with a `Consumer<String> progressHtml`; `QuestionModelImpl.ProgressThrottler` accumulates partial markdown in memory and at most every ~250 ms renders it with FlexMark and posts the HTML via `Platform.runLater`. **Partial text is never persisted** — storage sees SENT once and SUCCESS/FAIL once, exactly as before (mid-stream failures drop the partial buffer and take the normal FAIL path). `MediatorImpl.answerProgress(interactionId, answerType, html)` **guards on `stateModel.getCurrentInteractionId()`** — essential so a still-running stream for interaction A doesn't overwrite the pane after the user switches history to B — then routes to the right `AnswerVmMediator.displayPartialAnswer(html)` (status circle stays BLUE/SENT during streaming). `AnswerController` needed zero changes; Resend/⟳ regenerate/follow-ups all stream for free since they funnel through `MediatorImpl.requestAnswer`. GRAMMAR streams too (same `OpenAiApiImpl` binding) — not worth special-casing.

Test notes: `BaseMockApi` implements the 3-arg `send` and offers `putStreamingResponse(contains, List<String> chunks, perChunkDelay)` (regular `putResponse` emits its content as one delta); `RequestAnswerStreamingTest` covers cumulative FX-thread snapshots, SENT-until-terminal storage, and no-partial-on-FAIL. `StorageModel.newInteractionId()` starts from `Instant.now().getEpochSecond()` but is **strictly monotonic** (`max(epochSecond, lastIssued + 1)`, seeded from the max stored id and bumped by `saveInteraction`), so back-to-back interactions get distinct ids even within the same second and never overwrite each other.

### Concurrency invariants

Established by a 2026-07 concurrency review (with fixes applied); preserve these when changing cross-thread code:

- Two thread groups only: the FX thread (all view/viewmodel/state work) and `QuestionModelImpl.EXECUTOR`, a static cached pool running the 4 blocking/streaming AI sends. The pool uses **daemon threads** on purpose: streaming sends have no overall timeout and nothing ever shuts the pool down, so non-daemon threads would keep the JVM alive after the window closes.
- Background threads touch shared state **only** via `StorageModel`'s `synchronized` methods (terminal answer writes through `QuestionModelImpl.updateAnswer` → `updateInteraction` → `saveInteraction`) and re-enter the UI only via `Platform.runLater`. Every method in `StorageModelImpl`/`StateModelImpl` is `synchronized` — keep new ones that way.
- `StorageModelImpl.getTopics()` returns a **defensive copy**: `saveInteraction` MRU-reorders the live `topicList` on executor threads, so handing out the live list would race FX-thread iteration (this was a real `ConcurrentModificationException` bug).
- `StorageModelImpl.updateInteraction` on a nonexistent id is a **warn-and-skip no-op** — a streaming answer may finish after the user deleted its interaction, and the late write must not resurrect it.
- `MediatorImpl.answerProgress` **and** `answerUpdated` both guard on `stateModel.getCurrentInteractionId()`: a stream still running (or completing) after the user navigated to another interaction must not repaint the pane — an unguarded `answerUpdated` would revert a currently-streaming pane's partial HTML to the stored stale/empty answer. Both guards are unit-tested in `AnswerCallbackGuardTest` (plain Mockito on `MediatorImpl`, no FX toolkit needed).

### FXML loading and styling

- **Controllers are created by Guice, not by FXML's default reflection.** Gluon Ignite's `GuiceContext` (built in `TopicPromptUiApplication`) installs `setControllerFactory(guiceContext::getInstance)` on the single `FXMLLoader` it provides, and nested `fx:include` loaders inherit that factory — which is why every controller needs an explicit `bind(...)` in `ViewModule` (`RootModule` sets `requireExplicitBindings()`). The in-code comments claiming "FXMLLoader instantiates this controller itself" describe the effect (no-arg ctor + `@Inject` fields), not the mechanism.
- **Never `@Inject` an `FXMLLoader` outside `TopicPromptUiApplication`.** It is bound *only* by Ignite's `GuiceContext`, which exists solely when the app boots; with `requireExplicitBindings` an `@Inject Provider<FXMLLoader>` anywhere in the object graph fails the **entire** injector at creation, including in tests that build a bare `RootModule` (`CreationException: Explicit bindings are required and FXMLLoader is not explicitly bound`) — this took out ~20 unrelated model/core tests once. For a secondary FXML (dialogs), use a plain `new FXMLLoader(url)` and let FXML instantiate the controller reflectively; that works as long as the controller has no injected collaborators. `AnswerController.onAnswerButtonClick` is the reference example, loading `AnswerDetailsDialog.fxml` → `AnswerDetailsDialogController` (deliberately *not* Guice-bound). Note an `FXMLLoader` keeps the root/controller of its last load and cannot be reused — one loader per open.
- **FXML `$id` references cannot point forward, and fail silently.** `labelFor="$topicComboBox"` on a `Label` declared *before* the combo throws nothing and simply leaves the property unset (caught only by `HotKeysUiTest.altTFocusOnTopicComboBox`). This is why `TopicController` still calls `topicLabel.setLabelFor(topicComboBox)` in Java rather than declaring it — don't "clean that up".
- **Dialogs**: the Answer Info dialog is FXML (`AnswerDetailsDialog.fxml`, a `DialogPane` root declaring its own `buttonTypes`); the topic add/rename/delete dialogs in `TopicController` stay programmatic because FXML can't declare a prebuilt `TextInputDialog`/`Alert`'s editor or header. Per-pane text like the answer captions in `AnswerVmImpl` must stay in Java too — `Answer.fxml` is included 4× and FXML can't parameterize an `fx:include`.
- **Styling lives in `src/main/resources/topicpromptui/ui/view/app.css`**, attached declaratively with `stylesheets="@app.css"` on the `TopicPromptUi.fxml` root and on the `AnswerDetailsDialog.fxml` root (a dialog is its own scene graph and does not inherit the main scene's stylesheet). `QuestionStyle`'s constants are **style-class names**, not CSS text; `QuestionController` swaps the class with a one-way listener since a style class can't be bound like a property, and `QuestionVmProperties.questionTaStyle` is seeded with `QUESTION_STYLE_EMPTY` so exactly one `question-*` class is always applied (`question-empty` intentionally has no rule). When asserting a CSS-driven colour, remember Modena renders `-fx-control-inner-background` as a gradient whose **bottom stop** is the colour — see the helper in `FollowUpQuestionUiTest`.

### JPMS module-info

`src/main/java/module-info.java` explicitly `exports`/`opens` every package that Guice, Gson, or FXML need reflective/runtime access to. **When adding a new package, or a new class that Guice/Gson/FXML must reach reflectively, add the corresponding `exports`/`opens` entry** or the app will fail at runtime with module-access errors, not compile errors.

### Testing conventions

- `BaseTopicPromptUiTest` (extends TestFX `ApplicationTest`) boots the real `TopicPromptUiApplication` with `Modules.override(new RootModule()).with(new TestRootModule())` — `TestRootModule` swaps in `MockOpenAiApi`/`MockGcpApi`, `SoundServiceMock`, and an in-memory Jimfs filesystem. Most UI-level tests (`topicpromptui.ui.*`) extend this and drive the app through TestFX robot calls against real FXML scenes. **Naming convention: every class extending `BaseTopicPromptUiTest` is named `*UiTest`** (not plain `*Test`), so the heavyweight full-app-boot tests are distinguishable at a glance from lightweight single-model tests; keep new subclasses to this suffix. (`*UiTest` still ends in `Test` and is unaffected by the `*IT` integration-test exclusion, so `useJUnitPlatform` discovers and runs them normally.) A few `*UiTest` classes — e.g. `StateModelUiTest` — are really model tests that extend `BaseTopicPromptUiTest` only for the booted FX toolkit / DI context, not to drive the view; the suffix follows the base class, not the tested layer.
- Model-level tests (e.g. `StorageFilesystemTest`, `StorageModelTest`) test a single model directly, often with Jimfs for filesystem isolation, and do **not** extend `BaseTopicPromptUiTest` (hence the plain `*Test` suffix).
- **Keyboard-driven TestFX tests are unreliable on the live desktop.** Robot-synthesized key events are delivered to whichever window holds X input focus — if the user touches the terminal/another window mid-run, `press(...)`-based tests (accelerators, hotkeys) silently receive no key events and fail, while mouse-click tests keep passing (clicks are positional). This is why the Gradle `test` task runs on its own Xvfb + openbox virtual display by default (see the `test` block in `build.gradle`): the window-manager part matters too — ComboBox popup clicks don't register under a WM-less plain Xvfb, and openbox needs its empty keyboard/mouse config so its default `Ctrl+Alt+Up/Down` bindings don't swallow the app's hotkeys. If a hotkey test fails under `-PonRealDisplay`, re-run it with the default virtual display before concluding it's a code bug.
- `*IT.java` suffix marks integration tests that call real external APIs; keep new integration tests under this naming convention so `-PskipIntegrationTests` excludes them (and `-PskipUnitTests`, which conversely runs only `**/*IT.class`, includes them) correctly.
- **`*ApiIT` tests must build their injector with `ProjectTemplatesConfigurationModule` (test-only, in `src/test/java/topicpromptui/core/config/`) instead of the production `ConfigurationModule`.** `PromptFactoryImpl` copies each Freemarker template from the classpath into `<appDataPath>/templates` **only if it doesn't already exist there**, then always renders the on-disk copy — so an IT wired to the real `ConfigModel` renders `~/.topic-prompt-ui/templates/*.ftl`, i.e. whatever the *installed* app happened to materialize back when it first ran, which silently stales out on every subsequent template edit in the repo (this really happened: the ITs were graded against a `grammar-system.ftl` several commits behind `src/main/resources/`). `ProjectTemplatesConfigurationModule` binds `ConfigModel` to `ProjectTemplatesConfigModel`, which delegates `getProperty` to the real `ConfigModelImpl` (so live API keys still come from `~/.topic-prompt-ui/config.properties`) but returns a fresh Jimfs path from `getAppDataPath()`, forcing the copy-from-classpath branch every run. Unit tests get this for free — `TestRootModule` already binds `FileSystem` to Jimfs, so `ConfigModelImpl`'s own app-data path is empty.
- **`*ApiIT` graders are LLM-output assertions and are genuinely flaky** — `ResponseTextExactGrader`/`ResponseTextLengthGrader` failures come and go between runs on unchanged code (observed: a smart apostrophe `’` instead of `'`, a Claude answer overshooting a `[10-500]` length range, a capitalized term being "corrected" to lowercase). Re-run the class before treating a single red run as a regression.
- After `./gradlew test`, prefer reading `build/test-results/test/TEST-<FullyQualifiedClassName>.xml` for authoritative `tests`/`failures`/`errors` counts and captured `<system-out>` output — piping a full run through `tail -N` can truncate away the exact section you need (e.g. an `*IT` class that finishes early in a long combined run).
- When changing a hardcoded AI model name constant in `OpenAiModule`/`ClaudeModule`/`GcpModule`, verify it against the real provider API via the matching `*ApiIT` (e.g. `./gradlew test --tests "topicpromptui.core.ai.openai.OpenAiApiIT"`) before considering the change done — an invalid model name compiles fine but is rejected at request time (e.g. `model_not_found`).
